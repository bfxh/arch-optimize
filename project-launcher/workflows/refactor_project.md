# 项目重构工作流

## 触发条件

用户说"重构""重做""重新做""重新写"等，涉及对已有项目的重新构建。

## 执行铁律

1. **说了就做**：用户明确要做的事直接执行，不反问"需要我做吗"
2. **先问呈现再问技术**：重构需求先搞清楚用户想要什么效果，再问技术方案
3. **逐系统问完再推进**：多系统重构时，每个系统问完所有关键问题才进入下一个
4. **看完文档追问遗漏**：用户给了大量资料时，先通读再追问没说的部分

## 完整流程

### Step 1: 需求收集 (req-skill) — 重点：为什么不满意？

1. **第一个问题必须是**："你为什么要重构？哪里不满意？"
2. 搜索 memory 中该项目的过往记录
3. 如果之前有照片/截图 → **直接发给用户看**
4. 询问：
   - "你要不要看看之前是怎么做的？"
   - "之前哪里不满意？"
   - "这次想改进什么？"
5. 记录不满意的具体点 → 形成重构需求文档

### Step 2: 避坑检查 — 禁止自作聪明引用旧项目

**铁律清单**（逐条确认）：
- [ ] 不自动导入旧项目代码
- [ ] 不自动复制旧项目结构
- [ ] 不自动沿用旧项目配置
- [ ] 不自动"借鉴"旧项目实现
- [ ] 从零开始，或仅引用用户明确指定的部分

**例外**：用户明确说"参考之前的 xxx 部分"时，可以引用指定部分。

### Step 3: 架构审查 (arch-skill) — 隔离执行

1. 激活 `arch-optimize` 技能
2. 如果是对旧项目重构：
   - 先对旧项目执行架构扫描（`arch_optimize_scan`）
   - 执行风险诊断（`arch_optimize_risk_diagnose`）
   - 执行质量度量（`arch_optimize_quality_metrics`）
   - **记录旧项目的架构问题**，作为重构的改进方向
3. 如果是从零重构：
   - 直接进行架构规划
4. 输出独立的架构报告

### Step 4: 拉取领域技能 (pulled-skill)

1. 根据重构需求确定需要哪些专门技能
2. 检查本地知识库是否有缺失
3. 缺失 → 自动获取（执行知识自动获取协议）
4. 拉取的技能记录到 `.project-launcher/skill_index.json`

### Step 5: 文档生成 (doc-skill)

1. 生成 `REFACTOR_PLAN.md` — 重构方案
   - 包含：重构原因、改进方向、架构对比
2. 生成 `AVOID_PITFALLS.md` — 避坑清单
   - 列出旧项目的问题
   - 列出本次重构要避免的错误
3. 更新 `DESIGN.md` — 新架构设计
4. 更新 `CHANGELOG.md` — 记录重构变更

### Step 6: 输出重构包

```
重构包包含：
├── REFACTOR_PLAN.md    — 重构方案（含原因分析）
├── AVOID_PITFALLS.md   — 避坑清单
├── DESIGN.md           — 新架构设计
├── ARCH_REPORT.md      — 旧项目架构审查报告（独立）
├── CHANGELOG.md        — 变更日志
├── src/                — 新源代码目录（从零开始）
└── .project-launcher/
    ├── old_issues.json — 旧项目问题记录
    └── refactor_reasons.json — 重构原因记录
```

## 子智能体调度

- Step 1 (req) **必须串行先行**
- Step 2 (避坑检查) 在 Step 1 之后**必须执行**
- Step 3 (arch) **隔离执行**，可与其他步骤并行
- Step 4 (pulled) 可与 Step 3 并行
- Step 5 (doc) 依赖 Step 1 + Step 3 + Step 4 结果

## 质量检查

- [ ] 旧项目问题已全部记录
- [ ] 避坑清单已覆盖用户不满意的所有点
- [ ] 新架构不重复旧项目的架构错误
- [ ] 文档包含实际的分析结果，不是空壳
- [ ] 质量底线检查通过（见 `config/quality_standards.json`）
