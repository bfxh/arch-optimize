# 写作项目工作流

## 触发条件

用户说"写论文""写小说""写文档""写文章""写报告"等。

## 执行铁律

1. **说了就做**：用户明确要做的事直接执行，不反问"需要我做吗"
2. **先问呈现再问技术**：先搞清楚用户想要什么呈现效果，再问技术细节
3. **逐系统问完再推进**：多个章节/部分时，每个部分问完才进入下一个
4. **看完文档追问遗漏**：用户给了大量资料时，先通读再追问没说的部分

## 完整流程

### Step 1: 需求收集 (req-skill) — 分两层

#### 第一层：呈现方式（先于技术）

先问用户想要什么样的结果，而不是先问技术/内容方案：

1. **写作类型**：学术论文 / 小说 / 技术文档 / 报告
2. **呈现方式**：
   - 输出格式：Markdown / HTML / PDF / Word / LaTeX？
   - 视觉风格：正式 / 活泼 / 学术 / 技术极客？
   - 结构形态：长文 / 分章节 / 幻灯片 / 交互式？
   - 篇幅要求：大概多少字/页？
3. **目标读者**：给谁看？读者水平如何？
4. **目标效果**：用户心目中期望的最终效果是什么样

**禁止**：在这一层问"用什么研究方法""引用什么文献""怎么组织论点"——内容技术问题留到后面。

#### 第二层：内容与技术方案（呈现明确后才问）

1. **主题/研究方向**：具体写什么？
2. **内容深度**：综述级别 / 深度分析 / 原创研究？
3. **如果有用户提供的大量文档/资料** → **先通读全部**，然后追问：
   - "我看完你的文档了，还有几个没提到的点想确认..."
   - "文档里没覆盖 X 部分，你有没有补充材料？"
   - "这里内容和你的文档有出入，你倾向哪个版本？"
4. **反问机制**：
   - "之前写过类似的内容吗？哪里不满意？"
   - "有没有参考的范例？"
   - "对内容深度有什么具体要求？"
5. 如果 memory 中有历史写作素材 → **直接展示给用户看**
6. 输出 `需求摘要文档`

#### 需求确认
- 需求摘要输出后，用户确认才继续
- **但不要反问"需要我继续吗"**——直接展示摘要，说"确认后我开始"

### Step 2: 领域技能激活 (domain-skill → text)

1. 激活 `infrastructure/text/` 中的写作规范
2. 根据写作类型选择规范：
   - 学术写作 → `infrastructure/text/academic/`
   - 创意写作 → `infrastructure/text/creative/`
   - 技术文档 → `infrastructure/text/technical/`

### Step 3: 知识获取 (pulled-skill)

1. 检查写作主题相关的知识是否充足
2. 缺失 → 自动搜索获取（WebSearch + WebFetch）
3. 获取的内容组织到 `knowledge/` 目录
4. **铁律：缺什么就自动下什么，不说"未接收"**

### Step 4: 文档撰写 (doc-skill)

1. 创建写作大纲
2. **逐章节撰写**：每个章节问完用户需求后才写
3. **内容要求**：
   - 详细文档，内容充足
   - 不搞空壳
   - 包含实际的研究/调研结果
   - 即使工作已安排好，文档也要有实质内容
4. 生成参考资料索引

### Step 5: 输出

```
写作输出：
├── <文档名>.md           — 主文档
├── outline.md            — 大纲
├── references.md         — 参考资料
└── .project-launcher/
    └── knowledge_refs.json — 引用的知识来源
```

## 子智能体调度

- Step 1 (req) **必须串行先行**
- Step 2 (domain) + Step 3 (pulled) 可并行
- Step 4 (doc) 依赖 Step 1 + Step 2 + Step 3 结果

## 质量检查

- [ ] 呈现方式已明确（格式/风格/篇幅/读者）
- [ ] 用户提供的文档已全部通读
- [ ] 未覆盖的内容已追问用户
- [ ] 内容详实，不是空壳
- [ ] 参考资料有实际来源
- [ ] 格式符合写作类型规范
- [ ] 用户需求全部覆盖
