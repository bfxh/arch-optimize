# 新项目工作流

## 触发条件

用户说"开新项目""做一个新的""新建"等，且不是重构旧项目。

## 执行铁律

1. **说了就做**：用户明确要做的事直接执行，不反问"需要我做吗"
2. **先问呈现再问技术**：需求收集先搞清楚用户想要什么效果，再问技术方案
3. **逐系统问完再推进**：多系统项目每个系统问完所有关键问题才进入下一个
4. **看完文档追问遗漏**：用户给了大量资料时，先通读再追问没说的部分

## 完整流程

### Step 1: 需求收集 (req-skill) — 必须首先执行，分三层

#### 第一层：呈现方式（先于技术）

先问用户想要什么样的结果，而不是先问技术方案：

1. **项目类型**：游戏 / 软件 / 文本（无法从关键词判断时直接问）
2. **呈现方式**（按项目类型选择维度）：
   - 游戏项目：2D/3D？写实/风格化？什么视角？什么平台？
   - 软件项目：CLI/GUI/Web？什么交互形态？什么输出格式？
   - 文本项目：什么文档类型？什么格式？什么篇幅？什么读者？
3. **目标效果**：用户心目中期望的最终效果是什么样

**禁止**：在这一层问"用什么引擎""用什么框架""用什么算法"——技术问题留到后面。

#### 第二层：系统逐个反问（每个系统问完才进入下一个）

复杂项目有多个系统时，**逐个系统**收集需求。每个系统必须问完以下维度：

```
对每个系统 S：
  1. S 的核心功能是什么？
  2. S 的输入/输出是什么？
  3. S 和其他系统的关系？
  4. S 有什么特殊约束或偏好？
  5. S 有没有参考案例？
  → 用户确认 S 的需求完整后，才进入下一个系统
```

**游戏项目多维度反问清单**（必须逐维度问完）：

| 维度 | 必问问题 |
|------|---------|
| 核心玩法 | 什么类型？核心循环是什么？胜利/失败条件？ |
| 视觉风格 | 写实/风格化？参考作品？色调？分辨率？ |
| 物理系统 | 需要哪些物理模拟？刚体/柔体/流体？精度要求？ |
| 角色系统 | 角色数量？骨骼绑定方式？Motion Matching？肢体模块化？ |
| AI 行为 | NPC 智能？群体行为？难度曲线？ |
| 音频 | 程序化音频？音乐风格？3D 音效？ |
| 关卡设计 | 程序化生成/手工设计？关卡数量？规模？ |
| 资源管线 | 资源格式？流式加载？内存预算？ |
| 目标平台 | PC/主机/移动？性能预算？ |
| 世界构建 | 开放世界/线性？天气系统？昼夜循环？ |

**每个维度问完后**：确认用户没有补充，才进入下一个维度。

#### 第三层：技术方案（呈现和系统都明确后才问）

1. 基于已明确的呈现方式和系统需求，提出技术方案建议
2. 询问用户有无技术偏好（如 C/C++/Rust 优先）
3. 如果用户提供了大量文档/资料 → **先通读全部**，然后追问：
   - "我看完你的文档了，还有几个没提到的点想确认..."
   - "文档里没提到 X 系统，你有没有想法？"
   - "这里技术选型和你的文档有出入，你倾向哪个？"
4. 输出 `需求摘要文档`

#### 如果 memory 中有相关历史项目素材
- **直接展示给用户看**，不要只说"有记录"
- 展示后问："这个之前的项目你哪里不满意？"

#### 需求确认
- 需求摘要输出后，用户确认才继续
- **但不要反问"需要我继续吗"**——直接展示摘要，说"确认后我开始"

### Step 2: 项目类型检测 (domain-skill)

1. 根据 `skill_index.json` 中的 `project_type_detection` 关键词匹配
2. 匹配失败 → 直接问用户
3. 匹配成功 → 激活对应领域技能：
   - 游戏 → `infrastructure/game/`
   - 软件 → `infrastructure/software/`
   - 文本 → `infrastructure/text/`

### Step 3: 知识缺口检测 (pulled-skill)

1. 检查 `infrastructure/<type>/` 目录是否已有足够知识
2. 检查 `knowledge/sources.json` 是否已记录相关来源
3. 发现知识缺口 → 执行知识自动获取协议（见 `knowledge/auto_fetch.md`）
4. **铁律：永远不说"未接收"，缺什么就自动下载什么**

### Step 4: 基础设施搭建

1. 在用户指定目录（默认 `D:\开发\<项目名>`）创建项目结构
2. 复制 `infrastructure/<type>/` 中的模板到项目目录
3. 创建基础文件夹结构（非单个MD文件，是文件夹形式）
4. 更新 `infrastructure/_index.json` 索引

### Step 5: 架构规划 (arch-skill) — 隔离执行

1. 激活 `arch-optimize` 技能
2. 执行架构感知（阶段一）：扫描目录结构、识别技术栈
3. 输出架构规划建议
4. **架构审查与其他步骤隔离，不被业务逻辑干扰**

### Step 6: 文档生成 (doc-skill)

1. 生成 `README.md` — 项目说明
2. 生成 `DESIGN.md` — 技术设计
3. 生成 `REQUIREMENTS.md` — 需求文档（来自 Step 1）
4. 生成 `CHANGELOG.md` — 变更日志（初始版本）
5. **文档必须内容详实，不搞空壳**

### Step 7: 输出项目启动包

```
项目启动包包含：
├── REQUIREMENTS.md     — 需求文档（用户已确认）
├── DESIGN.md           — 架构设计
├── README.md           — 项目说明
├── CHANGELOG.md        — 变更日志
├── src/                — 源代码目录
├── docs/               — 文档目录
├── tests/              — 测试目录
├── assets/             — 资源目录（游戏项目）
└── .project-launcher/  — 启动器元数据
    ├── skill_index.json — 本次激活的技能索引
    └── knowledge_refs.json — 引用的知识来源
```

## 子智能体调度

- Step 1 (req) **必须串行先行**
- Step 2 (domain) + Step 3 (pulled) 可并行
- Step 4 (infrastructure) 依赖 Step 2 结果
- Step 5 (arch) **隔离执行**，可与 Step 6 (doc) 并行
- Step 6 (doc) 依赖 Step 1 + Step 5 结果

## 质量检查

完成前必须通过 `references/quality_checklist.md` 中的检查项。
