# 项目启动器 (Project Launcher)

## 定位

本技能是**元编排技能**（Meta-Orchestration Skill），在用户开始任何新项目、重构旧项目、或撰写内容时**必须默认唤起**。它不直接执行具体工作，而是编排5个子技能协同运作，确保每次启动都遵循正确的流程。

**铁律：用户说"写""做""重构""开新项目"时，第一个动作就是唤起本技能。**

**执行铁律（不可违反）**：
1. **说了就做**：用户明确要做的事直接执行，不反问"需要我做吗""要不要我更新"。用户说了是命令，不是建议。
2. **先问呈现再问技术**：需求收集先搞清楚用户想要什么效果，再问技术方案。
3. **逐系统问完再推进**：多系统项目每个系统问完所有关键问题才进入下一个。
4. **看完文档追问遗漏**：用户给了大量资料时，先通读再追问没说的部分。

## 五大子技能编排

本技能管理5个子技能，通过 `config/skill_index.json` 索引控制激活状态。每个项目**分情况处理**，不会一次性全部激活。

### 技能索引与激活控制

```
config/skill_index.json 结构：
{
  "skills": {
    "domain":    { "active": true,  "priority": 1, "description": "项目专属技能" },
    "arch":      { "active": true,  "priority": 2, "description": "架构技能" },
    "pulled":    { "active": false, "priority": 3, "description": "拉取的领域技能" },
    "doc":       { "active": true,  "priority": 4, "description": "文档技能" },
    "req":       { "active": true,  "priority": 5, "description": "需求技能" }
  },
  "defaults": {
    "new_project":    ["req", "domain", "arch", "doc"],
    "refactor":       ["req", "arch", "pulled", "doc"],
    "writing":        ["req", "doc"]
  }
}
```

### 5个子技能详解

#### 1. 项目专属技能 (domain-skill)

**作用**：根据项目类型拉取对应的领域技能。

| 项目类型 | 拉取的领域技能 | 来源 |
|---------|--------------|------|
| 游戏项目 | 游戏设计、程序化音频、Motion Matching 等 | `infrastructure/game/` + 在线获取 |
| 软件项目 | 架构模式、编码规范、测试框架 等 | `infrastructure/software/` + 在线获取 |
| 文本项目 | 文档写作、论文规范、叙事结构 等 | `infrastructure/text/` + 在线获取 |

**自动检测项目类型**：
- 关键词检测：游戏/game/engine/引擎 → 游戏项目
- 关键词检测：软件/software/app/服务 → 软件项目
- 关键词检测：论文/小说/文档/文章 → 文本项目
- 无法确定时：**直接问用户**，不猜测

#### 2. 架构技能 (arch-skill)

**作用**：针对整个架构独立审查，不被其他内容干扰。

**调用**：激活 `arch-optimize` 技能执行架构感知 → 风险诊断 → 质量度量。

**关键原则**：
- 架构审查与其他子技能**隔离执行**
- 先诊断后修复，诊断期间绝不提修复建议
- 输出独立的架构报告，不混入其他内容

#### 3. 拉取的领域技能 (pulled-skill)

**作用**：根据具体项目需求，从外部拉取专门的技能。

**拉取流程**：
1. 分析项目需求，确定需要哪些专门技能
2. 检查本地 `knowledge/` 目录是否已有相关知识
3. 缺失的知识 → 自动从网上下载（见知识获取协议）
4. 将获取的知识组织到 `infrastructure/<type>/` 对应目录

**默认不激活**：此技能需要根据项目具体情况决定是否拉取，避免过度加载。

#### 4. 文档技能 (doc-skill)

**作用**：负责撰写所有项目文档。

**文档类型**：
- 项目说明文档（README / DESIGN.md）
- 技术设计文档
- API 文档
- 变更日志
- 最终报告

**质量要求**：
- 文档必须内容详实，不搞空壳
- 即使智能体已安排好工作，文档里也要有实质内容
- 包含实际的研究/调研结果，不是声称"存在"

#### 5. 需求技能 (req-skill)

**作用**：反复搞明白用户的真实需求。

**核心流程（三层）**：
1. **第一层：呈现方式**（先于技术）— 先问用户想要什么效果（视觉/格式/交互），再问技术方案
2. **第二层：逐系统反问** — 多系统项目每个系统问完所有关键维度才进入下一个
3. **第三层：技术方案** — 呈现和系统都明确后才讨论技术选型

**反问机制**：
- "你为什么不喜欢某个东西？"
- 如果之前的项目有照片/截图 → **直接发给用户看**
- 用户看完后回答哪里不满意 → 更新需求
- 如果用户提供了大量文档 → **先通读全部**，再追问没说的部分
- 循环直到需求明确

**关键规则**：
- 需求不明确时**绝不开始实现**
- 有历史项目素材时**主动展示**给用户
- 用户说"不满意"时**追问具体原因**，记录到需求文档
- **说了就做**：用户明确要做的事直接执行，不反问"需要我做吗"
- **先问呈现再问技术**：不要上来就问技术方案
- **逐系统问完再推进**：每个系统问完才进入下一个

## 知识自动获取协议

### 铁律：拒绝"未接收"

**绝对禁止**对用户说"未接收""不支持""无法获取"等话术。当缺少相关知识或文档时：

1. **立即搜索**：使用 WebSearch 搜索相关资料
2. **下载获取**：使用 WebFetch 获取详细内容
3. **安装配置**：需要安装的工具/库/框架 → 直接安装配置
4. **组织入库**：将获取的知识组织到 `knowledge/` 和 `infrastructure/` 目录
5. **通知用户**：告知已获取了什么，而不是告知缺少什么

### 知识获取流程

```
检测到知识缺口
    ↓
Step 1: WebSearch 搜索关键词 + "latest" + "best practices"
    ↓
Step 2: WebFetch 获取权威来源详细内容
    ↓
Step 3: 提取核心知识，组织为结构化文档
    ↓
Step 4: 存入 infrastructure/<project-type>/ 对应子目录
    ↓
Step 5: 更新 knowledge/sources.json 记录来源
    ↓
Step 6: 通知用户 "已获取并配置完成：[具体内容列表]"
```

### 基础设施文件管理

基础设施使用**文件夹形式**（非单个MD文件），具有有效索引：

```
infrastructure/
├── game/           # 游戏项目基础设施
│   ├── engines/    # 引擎知识
│   ├── rendering/  # 渲染技术
│   ├── physics/    # 物理模拟
│   ├── audio/      # 程序化音频
│   └── assets/     # 资源管理
├── software/       # 软件项目基础设施
│   ├── patterns/   # 设计模式
│   ├── testing/    # 测试框架
│   ├── ci-cd/      # 持续集成
│   └── security/   # 安全规范
├── text/           # 文本项目基础设施
│   ├── academic/   # 学术写作
│   ├── creative/   # 创意写作
│   └── technical/  # 技术文档
└── _index.json     # 基础设施索引文件
```

## 项目重构避坑原则

### 原则一：禁止自作聪明引用旧项目

**铁律：每次重构新项目，绝不自动引用用户的旧项目。**

即使用户保存了旧项目：
- 不自动导入旧项目代码
- 不自动复制旧项目结构
- 不自动沿用旧项目配置
- 不自动"借鉴"旧项目实现

### 原则二：主动复盘与询问

重构前**必须执行**：

1. **搜索历史**：检查 memory 中是否有该项目的过往记录
2. **主动询问**：
   - "你要不要看看之前是怎么做的？"
   - "之前哪里不满意？"
   - "这次想改进什么？"
3. **记录原因**：用户因为不满意才会重构 → 记录不满意的具体点
4. **展示证据**：如果之前有照片/截图 → 直接发给用户看

### 原则三：明确审美与质量底线

**用户明确讨厌的行为**（记录在 `config/quality_standards.json`）：

| 禁止行为 | 正确做法 |
|---------|---------|
| 用低模球体代替人物 | 使用真实建模或程序化生成 |
| 树木像拼积木、纹理差 | 使用物理规则驱动的树木生成 |
| 拿一个球说这是人物 | 最低限度也要有正确的拓扑结构 |
| "指鹿为马"式的识别错误 | 如实报告，不虚构 |
| 声称存在但不展示 | 实际展示调研/研究结果 |

**质量底线公式**：
```
质量底线 = max(用户明确要求, 领域最佳实践, 真实性标准)
```

- **真实性优先**：物理规则驱动 > 贴图拼接 > 低模占位
- **宁可不做，不可做差**：如果做不到真实效果，先告知用户而非用劣质替代
- **反对虚假**：绝对禁止用占位符冒充成品

## 工作流

### 工作流一：新项目

详见 `workflows/new_project.md`

```
1. 唤起 req-skill → 收集需求（含反问+展示历史素材）
2. 检测项目类型 → 激活 domain-skill
3. 检查知识缺口 → 自动获取缺失知识
4. 搭建基础设施 → 创建文件夹结构
5. 激活 arch-skill → 架构规划
6. 激活 doc-skill → 生成项目文档
7. 输出：项目启动包（需求文档+架构设计+基础设施+知识库）
```

### 工作流二：项目重构

详见 `workflows/refactor_project.md`

```
1. 唤起 req-skill → 明确重构原因（为什么不满意旧的？）
2. 搜索历史 → 主动展示之前的问题/截图
3. 禁止引用旧项目代码 → 从零开始或用户明确指定部分
4. 激活 arch-skill → 架构审查（独立执行）
5. 激活 pulled-skill → 拉取需要的领域技能
6. 激活 doc-skill → 记录重构决策和变更
7. 输出：重构方案+避坑清单+架构报告
```

### 工作流三：写作项目

详见 `workflows/writing_project.md`

```
1. 唤起 req-skill → 明确写作主题和要求
2. 激活 domain-skill (text) → 拉取写作规范
3. 检查知识缺口 → 自动获取相关资料
4. 激活 doc-skill → 执行写作
5. 输出：完整文档+参考资料索引
```

## 子技能调度与子智能体

根据用户规则"开启子代理 子智能"，本技能支持将子技能分派给子智能体并行执行：

- **可并行的**：domain-skill + doc-skill（互不依赖时）
- **必须串行的**：req-skill → 其他技能（需求先行）
- **独立隔离的**：arch-skill（架构审查不受其他干扰）

调度原则：
- 隔离可调，允许不完全隔离
- 强相关项目支持并行窗口（编辑器/引擎/游戏作为一体）
- 子智能体根据任务进度进行条件编排

## 设计理念

1. **说了就做**：用户明确要做的事直接执行，不反问"需要我做吗"。用户说了是命令，不是建议。
2. **先问呈现再问技术**：需求收集先搞清楚用户想要什么效果，再问技术方案
3. **逐系统问完再推进**：多系统项目每个系统问完所有关键问题才进入下一个
4. **看完文档追问遗漏**：用户给了大量资料时，先通读再追问没说的部分
5. **需求先行**：搞明白需求再动手，反复确认而非一次定论
6. **知识自补**：缺失的知识自动获取，永远不说"未接收"
7. **架构隔离**：架构审查独立执行，不被业务逻辑干扰
8. **拒绝复用旧项目**：重构从零开始，不自动引用旧代码
9. **真实优于占位**：宁可不做，不用劣质替代冒充成品
10. **索引控制**：通过索引灵活控制技能激活，分情况处理
11. **文档有实质**：文档必须包含实际内容，不是空壳
12. **子智能协作**：支持子代理并行，按进度条件编排
