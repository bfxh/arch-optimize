# 质量度量参考文档

本文档定义架构优化技能使用的全部量化指标和评分体系。

---

## 一、维护性指数 (Maintainability Index, MI)

来源：Microsoft 提出，SonarQube / Visual Studio 广泛采用

### 1.1 公式

```
MI = MAX(0, (171 - 5.2 × ln(HV) - 0.23 × CC - 16.2 × ln(LOC)) × 100 / 171)
```

### 1.2 参数说明

| 参数 | 含义 | 计算方式 |
|------|------|---------|
| HV | Halstead Volume（代码容量） | Length × log2(Vocabulary) |
| CC | Cyclomatic Complexity（圈复杂度） | e - n + 2p |
| LOC | Lines of Code（代码行数） | 非空非注释行 |

**Halstead 参数**：
- n1 = 不同运算子数量
- n2 = 不同操作数数量
- N1 = 运算子出现总次数
- N2 = 操作数出现总次数
- Vocabulary = n1 + n2
- Length = N1 + N2
- Volume = Length × log2(Vocabulary)

**圈复杂度**：
- e = 控制流图边数
- n = 判定节点数
- p = 独立组件数

### 1.3 评分解读

| MI 范围 | 等级 | 颜色 | 含义 |
|---------|------|------|------|
| MI > 20 | 高可维护性 | 🟢 绿色 | 代码清晰，易于维护 |
| 10 ≤ MI ≤ 20 | 中等 | 🟡 黄色 | 有改善空间 |
| MI < 10 | 低可维护性 | 🔴 红色 | 需要重构 |

### 1.4 使用场景

- 评估单个函数/文件的可维护性
- 对比重构前后的质量变化
- 识别高复杂度热点
- 质量门禁：新增代码 MI ≥ 15

## 二、EvoScore 演进评分

来源：SWE-CI 基准测试（中山大学+阿里，arXiv:2603.03823）

### 2.1 核心公式

```
         Σ(i=1 to N) γ^i × a(c_i)
EvoScore = ─────────────────────────
              Σ(i=1 to N) γ^i
```

### 2.2 归一化变化 a(c)

设 n(c) 为代码库 c 通过的测试用例数：

```
         ⎧ (n(c) - n(c_0)) / (n(c_*) - n(c_0))   若 n(c) ≥ n(c_0)  [改进]
a(c) =   ⎨
         ⎩ (n(c) - n(c_0)) / n(c_0)               否则              [退步]
```

- c_0 = 基线代码库
- c_* = 目标代码库
- c = 当前代码库

### 2.3 非对称设计原理

**改进时**：按目标差距归一化 → 满分 = 1.0（完全达成目标）

**退步时**：按原有基线归一化 → 最差 = -1.0（完全破坏所有功能）

**深层逻辑**：破坏现有功能的代价 > 增加新功能的收益。引入回归错误是极其严重的问题。

### 2.4 权重参数 γ

| γ 值 | 效果 | 适用场景 |
|------|------|---------|
| γ = 1 | 简单平均，所有迭代一视同仁 | 短期项目 |
| γ = 1.5 | 后期迭代权重略高 | 常规项目 |
| γ = 2.0 | 后期迭代权重显著上升 | 长期维护项目 |
| γ = 3.0 | 极度重视长期质量 | 核心系统/基础设施 |

**核心洞察**：真正可维护的代码应在长期演化中表现越来越好，而非越来越差。早期草率决策的负面影响会随项目发展越来越明显。

### 2.5 策略诊断

通过调节 γ 值可以区分两种开发策略：
- **"短期收益"策略**：快速但不够稳固的修改，低 γ 时表现好
- **"长期投资"策略**：初期进展慢但建立坚实基础，高 γ 时表现更好

## 三、健康分模型

来源：brooks-lint

### 3.1 计算公式

```
健康分 = 100 - 15 × Critical数 - 5 × Warning数 - 1 × Suggestion数
```

最低为 0，不出现负数。

### 3.2 严重性定义

| 级别 | 扣分 | 含义 | 行动 |
|------|------|------|------|
| 🔴 Critical | -15 | 严重影响可维护性/正确性 | 必须修复 |
| 🟡 Warning | -5 | 有改善空间 | 建议修复 |
| 🟢 Suggestion | -1 | 可选优化 | 记录跟踪 |
| ℹ️ Info | 0 | 信息性 | 无需行动 |

### 3.3 健康分等级

| 分数范围 | 等级 | 含义 |
|---------|------|------|
| 90-100 | 优秀 | 代码库健康状况良好 |
| 70-89 | 良好 | 有少量技术债 |
| 50-69 | 需关注 | 有较多技术债 |
| 0-49 | 危险 | 需要紧急重构 |

### 3.4 质量门禁

| 门禁 | 阈值 | 类型 |
|------|------|------|
| 合并门禁 | 健康分 ≥ 70 | 软性门禁 |
| 发布门禁 | 健康分 ≥ 80 | 硬性门禁 |
| 新代码 | MI ≥ 15 | 硬性门禁 |
| 零退化率 | = 100% | 硬性门禁 |

### 3.5 历史趋势追踪

每次审查后记录：
```json
{
  "date": "2026-07-25",
  "mode": "full-audit",
  "score": 78,
  "critical": 2,
  "warning": 5,
  "suggestion": 8,
  "scope": "internal/agent/"
}
```

报告显示趋势线：`85 → 82 (−3) over last 3 runs`

## 四、Pain × Spread 技术债优先级矩阵

来源：brooks-lint

### 4.1 Pain 评分（痛点强度）

| 分数 | 描述 |
|------|------|
| 3 | 开发者主动回避该区域；大多数改动引发 bug |
| 2 | 该区域明显比其他地方慢 |
| 1 | 质量问题但当前无活跃痛点 |

### 4.2 Spread 评分（影响范围）

| 分数 | 描述 |
|------|------|
| 3 | 影响 5+ 模块或全团队 |
| 2 | 影响 2-4 模块或部分团队 |
| 1 | 隔离在一个模块或一个开发者区域 |

### 4.3 优先级矩阵

| Priority (Pain×Spread) | 分类 | 行动时间线 |
|------------------------|------|-----------|
| 7-9 | Critical debt | 下个迭代解决 |
| 4-6 | Scheduled debt | 季度内规划 |
| 1-3 | Monitored debt | 记录监控 |

### 4.4 债务类型区分

| 类型 | 特征 | 处理方式 |
|------|------|---------|
| 有意债务 (Intentional) | 有 owner、有 ticket、有偿还计划 | 按计划执行 |
| 无意债务 (Unintentional) | 结构性侵蚀，无计划产生 | 优先偿还 |
| 腐烂债务 (Rot) | 长期未处理，可能已无关 | 评估后删除或归档 |

## 五、SQALE 技术债模型

来源：SonarQube SQALE 方法

### 5.1 技术债比率

```
技术债比率 = 修复成本 / 开发成本
```

- **修复成本**：修复所有代码异味所需的估算时间
- **开发成本**：开发软件的成本（通常按行数 × 每行分钟数估算）

### 5.2 技术债评级

| 评级 | 比率范围 | 含义 |
|------|---------|------|
| A | < 5% | 极低技术债 |
| B | 5% - 10% | 低技术债 |
| C | 10% - 20% | 中等技术债 |
| D | 20% - 50% | 高技术债 |
| E | > 50% | 极高技术债 |

### 5.3 代码异味修复时间估算

| 异味类型 | 估算修复时间 |
|---------|-------------|
| 方法过长 | 20 分钟/10 行 |
| 圈复杂度高 | 30 分钟/点 |
| 重复代码 | 15 分钟/块 |
| 深层嵌套 | 25 分钟/层 |
| 上帝类 | 2 小时/类 |
| 贫血模型 | 1.5 小时/模型 |

## 六、综合质量仪表盘

### 6.1 四维评分卡

| 维度 | 指标 | 权重 | 数据来源 |
|------|------|------|---------|
| 架构健康 | 健康分 | 30% | 六大衰退风险扫描 |
| 代码可维护性 | 平均 MI | 25% | 静态分析 |
| 演进质量 | EvoScore | 25% | 测试通过率追踪 |
| 技术债 | SQALE 评级 | 20% | 代码异味扫描 |

### 6.2 综合评分公式

```
综合质量分 = 健康分 × 0.30 + (MI/20 × 100) × 0.25 + EvoScore × 100 × 0.25 + (100 - SQALE比率×2) × 0.20
```

### 6.3 仪表盘输出示例

```
┌─────────────────────────────────────┐
│     项目质量仪表盘 - 2026-07-25     │
├─────────────────────────────────────┤
│ 架构健康:  78/100  🟡              │
│ 代码可维护: 14.3/20  🟡            │
│ 演进质量:  0.72  🟢                │
│ 技术债:    C级 (12%)  🟡          │
│─────────────────────────────────────│
│ 综合评分:  74.2/100  🟡 良好       │
│ 零退化率:  100%  🟢               │
```

## 七、Triage 流程

### 7.1 发现处置选项

| 选项 | 含义 | 效果 |
|------|------|------|
| Accept | 接受为有效发现 | 计入健康分 |
| Dismiss | 降级为 Info | 不扣分，记录原因 |
| Defer | 延期处理 | 90 天后重新浮现 |
| Skip | 跳过 | 不记录 |

### 7.2 Dismiss 理由（必须记录）

- 假阳性（属于假阳性例外列表）
- 有意设计决策（需链接 ADR）
- 测试专用代码
- 迁移期临时代码（需标注截止日期）
