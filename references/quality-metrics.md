## 一、维护性指数 (Maintainability Index, MI)

来源：Microsoft 提出，SonarQube / Visual Studio 广泛采用

### 1.1 公式

```
MI = MAX(0, (171 - 5.2 × ln(HV) - 0.23 × CC - 16.2 × ln(LOC)) × 100 / 171)
```

### 1.2 参数说明

| 参数 | 含义 | 计算方式 |
|------|------|---------|
| HV | Halstead Volume（代码容量） | Length × log2(Vocabulary) |
| CC | Cyclomatic Complexity（圈复杂度） | e - n + 2p |
| LOC | Lines of Code（代码行数） | 非空非注释行 |

**Halstead 参数**：
- n1 = 不同运算子数量
- n2 = 不同操作数数量
- N1 = 运算子出现总次数
- N2 = 操作数出现总次数
- Vocabulary = n1 + n2
- Length = N1 + N2
- Volume = Length × log2(Vocabulary)

**圈复杂度**：
- e = 控制流图边数
- n = 判定节点数
- p = 独立组件数

### 1.3 评分解读

| MI 范围 | 等级 | 颜色 | 含义 |
|---------|------|------|------|
| MI > 20 | 高可维护性 | 🟢 绿色 | 代码清晰，易于维护 |
| 10 ≤ MI ≤ 20 | 中等 | 🟡 黄色 | 有改善空间 |
| MI < 10 | 低可维护性 | 🔴 红色 | 需要重构 |

> **刻度说明**：1.1 的公式已乘 `100/171`，脚本输出与上表档位同处 **0–100** 刻度（与 Visual Studio 的归一化 MI 及其默认阈值 20 一致），刻度本身是配套的。真正要防的是下面这条粒度问题。
>
> **计算粒度**：文献与 IDE 中 MI 通常**按方法**计算；本脚本按**整文件**计算 HV/CC/LOC，`16.2·ln(LOC)` 使结果随文件长度单调下降。实测同一风格的直线代码：12 行 → 59.2，40 行 → 43.3，132 行 → 27.6，332 行 → 15.6。因此"MI 低"首先是"文件大"的信号：要评价单个函数请配合 `--min-cc` 看函数级 CC，不要直接用整文件 MI 下结论。

### 1.4 使用场景

- 评估单个函数/文件的可维护性
- 对比重构前后的质量变化
- 识别高复杂度热点
- 质量门禁：新增代码 MI ≥ 15

脚本没有"新增代码"概念，该门禁需自己按改动文件逐个跑：

```bash
python scripts/quality_metrics.py --file <改动文件> --json | python -c "import json,sys; print(json.load(sys.stdin)['files'][0]['maintainability_index'])"
```

## 二、健康分模型

来源：brooks-lint

### 2.1 计算公式

```
健康分 = 100 - 15 × Critical数 - 5 × Warning数 - 1 × Suggestion数
```

最低为 0，不出现负数。

> **无规模归一**：扣分按发现条数的绝对值，与代码量无关。实测同一份内容：单个文件 85 分，复制成 20 份后 0 分。所以健康分只对"同一范围、同一口径"的前后两次扫描可比；跨项目、跨目录大小比较无意义。7 条 Critical 就足以把任何项目打到 0 分。并且 score 在 0 处**饱和**：实测 risk_diagnose 扫 8 个长函数文件（58 Critical）与 80 个（130 Critical）score 都是 0，量不出债务量级。还有一个与规模无关的上限：**这个分数衡量的是阈值触发次数，不是设计质量**。七类设计问题（`design-review.md` §一）没有任何一条进入扣分项，一个边界画错、不变量无人看守的模块可以拿 100 分。
>
> **密度字段（两个计分器都输出，口径一致=物理行数）**：`scanned_lines` 与 `penalty_per_kloc`（= 15C+5W+1S × 1000 / 行数）。纯复制下该密度不变（实测 quality_metrics 扫 8 份与 80 份同为 79.37，每文件 5 Warning/63 行），可跨项目比较；饱和场景也靠它恢复量级。`score` 保留绝对计数——门禁契约不动。
>
> **同一个分数有三份实现**：`quality_metrics.py`（来自 hotspots）、`risk_diagnose.py`（来自 R1-R6 发现）、`regression_guard.py`（来自回归/性能条数，且丢掉 Suggestion 项）。三者公式一致但输入集不同、覆盖文件集也不同，不要把两份数字当一个指标引用。

### 2.2 严重性定义

| 级别 | 扣分 | 含义 | 行动 |
|------|------|------|------|
| 🔴 Critical | -15 | 严重影响可维护性/正确性 | 必须修复 |
| 🟡 Warning | -5 | 有改善空间 | 建议修复 |
| 🟢 Suggestion | -1 | 可选优化 | 记录跟踪 |
| ℹ️ Info | 0 | 信息性 | 无需行动 |

### 2.3 健康分等级

| 分数范围 | 等级 | 含义 |
|---------|------|------|
| 90-100 | 优秀 | 代码库健康状况良好 |
| 70-89 | 良好 | 有少量技术债 |
| 50-69 | 需关注 | 有较多技术债 |
| 0-49 | 危险 | 需要紧急重构 |

### 2.4 质量门禁

| 门禁 | 阈值 | 类型 | 脚本实现情况 |
|------|------|------|--------------|
| 合并门禁 | 健康分 ≥ 70 | 软性门禁 | `risk_diagnose`/`quality_metrics` 给分数，不判红；需自行比较 |
| 发布门禁 | 健康分 ≥ 80 | 硬性门禁 | **无实现**，需自建 CI 判断 |
| 新代码 | MI ≥ 15 | 硬性门禁 | 需逐文件 `--file` 跑，见 1.4 |
| 零退化率 | = 100% | 硬性门禁 | `regression_guard compare` 退出码 1；删/改名测试可绕过（见 regression-guard.md） |

### 2.5 历史趋势追踪（手工记录，无脚本支持）

> 本仓没有任何脚本写出或读取这份历史：`regression_guard evoscore` 读的是迭代数组（字段 `iteration/passed/target/regressions`），与本节的 `score/critical/...` **字段不兼容**，两者不能互为输入。下面这份 JSON 是给人（或 agent）手工维护的格式，趋势线需自行比对。

每次审查后记录：
```json
{
  "date": "2026-07-25",
  "mode": "full-audit",
  "score": 78,
  "critical": 2,
  "warning": 5,
  "suggestion": 8,
  "scope": "internal/agent/"
}
```

报告显示趋势线：`85 → 82 (−3) over last 3 runs`

## 三、Pain × Spread 技术债优先级矩阵

来源：brooks-lint

> Pain/Spread 两项都要靠人的判断（谁在回避哪块、影响几个模块），脚本不产出这两个字段，也不产出下面的优先级分类。本节是阶段四排优先级的方法论，不是可自动判定的门禁。

### 4.1 Pain 评分（痛点强度）

| 分数 | 描述 |
|------|------|
| 3 | 开发者主动回避该区域；大多数改动引发 bug |
| 2 | 该区域明显比其他地方慢 |
| 1 | 质量问题但当前无活跃痛点 |

### 4.2 Spread 评分（影响范围）

| 分数 | 描述 |
|------|------|
| 3 | 影响 5+ 模块或全团队 |
| 2 | 影响 2-4 模块或部分团队 |
| 1 | 隔离在一个模块或一个开发者区域 |

### 4.3 优先级矩阵

| Priority (Pain×Spread) | 分类 | 行动时间线 |
|------------------------|------|-----------|
| 7-9 | Critical debt | 下个迭代解决 |
| 4-6 | Scheduled debt | 季度内规划 |
| 1-3 | Monitored debt | 记录监控 |

### 4.4 债务类型区分

| 类型 | 特征 | 处理方式 |
|------|------|---------|
| 有意债务 (Intentional) | 有 owner、有 ticket、有偿还计划 | 按计划执行 |
| 无意债务 (Unintentional) | 结构性侵蚀，无计划产生 | 优先偿还 |
| 腐烂债务 (Rot) | 长期未处理，可能已无关 | 评估后删除或归档 |

## 五、SQALE 技术债模型

来源：SonarQube SQALE 方法

> 脚本不计算修复时间、技术债比率或 A–E 评级（第五节的 6 类估时表全部为人工估算）。6.1 的"技术债"一维需人工填入。

### 5.1 技术债比率

```
技术债比率 = 修复成本 / 开发成本
```

- **修复成本**：修复所有代码异味所需的估算时间
- **开发成本**：开发软件的成本（通常按行数 × 每行分钟数估算）

### 5.2 技术债评级

| 评级 | 比率范围 | 含义 |
|------|---------|------|
| A | < 5% | 极低技术债 |
| B | 5% - 10% | 低技术债 |
| C | 10% - 20% | 中等技术债 |
| D | 20% - 50% | 高技术债 |
| E | > 50% | 极高技术债 |

### 5.3 代码异味修复时间估算

| 异味类型 | 估算修复时间 |
|---------|-------------|
| 方法过长 | 20 分钟/10 行 |
| 圈复杂度高 | 30 分钟/点 |
| 重复代码 | 15 分钟/块 |
| 深层嵌套 | 25 分钟/层 |
| 上帝类 | 2 小时/类 |
| 贫血模型 | 1.5 小时/模型 |

## 六、综合质量仪表盘

### 6.1 四维评分卡

| 维度 | 指标 | 权重 | 数据来源 |
|------|------|------|---------|
| 架构健康 | 健康分 | 30% | `risk_diagnose` 的 `health_score.score` |
| 代码可维护性 | 平均 MI | 25% | `quality_metrics` 的 `average_mi` |
| 技术债 | SQALE 评级 | 20% | 人工判定（脚本未实现，见第五节） |
| 回归防护 | 零退化率 | 25% | `regression_guard compare` 的 `zero_regression_rate` |

### 6.2 综合评分公式

四项均已归一到 0–100，权重合计 100%：

```
综合评分 = 0.30 × 健康分
         + 0.25 × 平均 MI
         + 0.20 × SQALE 得分        (A=100, B=80, C=60, D=40, E=20)
         + 0.25 × 零退化率(%)

等级：≥85 优 / 70–84 良 / 50–69 需关注 / <50 危险（与 2.3 健康分等级同刻度）
```

### 6.3 仪表盘输出示例

```
┌─────────────────────────────────────┐
│     项目质量仪表盘 - 2026-07-25     │
├─────────────────────────────────────┤
│ 架构健康:  78/100  🟡              │
│ 代码可维护: 62/100  🟢 (平均 MI)   │
│ 技术债:    C级 (12%)  🟡          │
│─────────────────────────────────────│
│ 综合评分:  75.9/100  🟡 良好       │
│ 零退化率:  100%  🟢               │
│ 趋势:      85 → 82 → 78 (↓7)     │
└─────────────────────────────────────┘
```

## 七、Triage 流程

### 7.1 发现处置选项

| 选项 | 含义 | 效果 |
|------|------|------|
| Accept | 接受为有效发现 | 计入健康分 |
| Dismiss | 降级为 Info | 不扣分，记录原因 |
| Defer | 延期处理 | 90 天后重新浮现 |
| Skip | 跳过 | 不记录 |

### 7.2 Dismiss 理由（必须记录）

- 假阳性（属于假阳性例外列表）
- 有意设计决策（需链接 ADR）
- 测试专用代码
- 迁移期临时代码（需标注截止日期）
