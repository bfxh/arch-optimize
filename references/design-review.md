# 设计评审参考文档

本文档定义**设计问题**是什么、怎么问、怎么下结论，以及为什么这五件事不能交给脚本。
`SKILL.md` 的「阶段零：设计判断」按本文执行；`architecture-principles.md` §四是脚本能判什么的唯一权威口径。

---

## 〇、为什么要有这一层

脚本给的是**码级卫生**阈值：函数多长、扇出几条、字面量重复几次、健康分扣几分。设计问题是**决策级**的——某个边界画在哪、某个抽象给谁用、某个不变量由谁守住——这类判断没有一条能写成阈值。

模型默认行为会绕开它：跑 5 个脚本、看分、把条数报出来，就交付了。这条路径的产物**看起来像架构评审**，实际是阈值告警的整理。它有个可验证的症状：健康分 100 的仓里可以有根本性的边界错误，而最重的那类设计问题在六个风险扫描里**零条发现**。

举例（都在这份技能自己的口径内成立）：
- 两个模块各自短小、命名清楚、无环、MI 高——如果它们被同一个变更原因切开，脚本一声不响（R2 只数 import 条数，"分散"表现为 import 少而干净）。
- 一个 `Order.cancel()` 同时退款并回滚库存，18 行、嵌套 2 层、CC 3。所有阈值全绿，因为没有任何指标衡量"一个方法是否表达了两个概念"。

所以这一层的做法不是加探测器，是**结构化提问**：先把七类问题各问一遍，再决定要不要跑脚本、跑哪些。

---

## 一、七类设计问题

每类给四件事：它在问什么、真实长什么样、去哪取证、为什么脚本看不到（或反而误导）。

### 1. 变化边界画错

**它在问**：上一次真实需求变更动了几个互不相关的目录？

**真实长什么样**：
- 加一个"用户备注"字段要改 `api/users.py`、`domain/user.py`、`report/pdf.py`、前端一处映射——四个地方，一个原因。
- `utils/helpers.py` 里同时放着日期格式化、重试退避和 CSV 转义——三个不相关的原因，一个文件。

**取证**：git 共变历史（最近 20–50 次提交里哪些文件总一起改）；最近 3 个已落地需求的 diff 文件集。这是唯一能证伪"边界合理"的证据，脚本里没有它的实现。

**脚本为什么看不到**：`dep_graph` 只看 import，而"同一原因被拆散"恰恰表现为 import 很少、依赖图很干净。R2 报的高扇出是"这个文件依赖很多模块"，与"这个变更原因散布在很多模块"不是同一件事。

### 2. 耦合的方向与强度

**它在问**：B 改了，A 会不会被迫改？如果是，A 用的是 B 的哪一部分？

**真实长什么样**：
- 领域层为了打一行日志，把 logger 类型穿过三层构造函数。
- 配置对象一路传到第 6 层，只为了最底层那个 `timeout` 常量。
- A 只调 B 的一个纯函数，却 import 了 B 的包初始化链，于是继承了 B 的全部依赖。

**取证**：R2 的扇出数字只用来**列候选**，然后人工看每个依赖实际用了对方暴露的哪一角。

**脚本为什么看不到**：一条 import 可能拖来整个接口，七条 import 可能各只取一个纯函数。条数是"怀疑预算"，不是耦合度。

### 3. 抽象的层次与位置

**它在问**：这个抽象有几个真实调用方？再加一个实现要动几个文件？

**真实长什么样**：
- 只有一个实现的接口**放在调用方那一层**通常是对的（面向自己需要的能力定义）；放在实现方那一层就是错的——调用方被迫依赖具体。
- `BaseService` 抽出 `save/update/delete`，三个子类都重写了签名并各自补了参数，抽象现在只锁住名字。
- 抽象的粒度比问题本身细：为了"扩展"把 12 行逻辑切成 5 个 hook。

**取证**：跨文件 grep 实现数与调用点数；问一句"如果明天要加第二种实现，第一个要改的文件是哪个"。

**脚本为什么看不到**：R4 按**单文件**数实现（抽象类与其唯一实现分处两文件检不出，同文件 `interface + class` 惯用写法必报）。"这个抽象是否多余"从来不是计数问题。

### 4. 不变量归属

**它在问**：如果这条约束被绕过，会在哪一行炸？谁会先发现？

**真实长什么样**：
- "余额不得为负"在 service 里检查，但 `account.balance -= x` 在模型上直接暴露，第二个入口绕过它。
- 同一个校验在两个入口各写一遍，条件已经不一致（一个 `< 0`，一个 `<= 0`）。
- 不变量只写在文档和注释里，代码里没有任何一处强制它。

**取证**：列出这个模块最重要的 3 条规则，逐条指出由哪一行、在哪一层保证；再找有没有第二条表达。

**脚本为什么看不到**：R3 抓的是**文本相似**，同一规则换个写法就不像了；R6 只问"这个类有没有方法"，有方法的贫血模型照样过。

### 5. 演化能力与可逆性

**它在问**：半年后要换掉 X，要动几个文件？有没有一条测试能告诉我换错了？

**真实长什么样**：
- HTTP 客户端的具体类型写在 30 个函数签名里——换库要动 30 个文件，且没有一条测试会红。
- 表结构直接映射到 API 响应，DB 加一列就等于对外契约变更。
- 一个决策散在配置、常量、文档三处，改的时候只有两处会生效。

**取证**：挑一个"最可能被推翻的假设"（供应商、存储、协议、计价规则），手动数改动面积；再看 `regression_guard` 的基线里有没有覆盖它。

**脚本为什么看不到**：回归防护守的是**行为**不变，不是**结构**可扩展。基线全绿与"换掉它很便宜"没有关系。

### 6. 概念到代码的映射保真（统一语言）

**它在问**：产品嘴里的那个词，在代码里有几个名字？这几个名字指的是同一个东西吗？

**真实长什么样**：
- `Order / Purchase / Checkout / Bill` 混用，其中两个是同一概念、另两个是不同概念。
- `status` 在表里是 int、在 API 里是 str、在校验里是硬编码数字 2。
- 一个方法名只说 `sync`，实际做两件事；或一个概念被摊到三个服务里，没有一个地方说清它。

**取证**：从需求文档/接口里抄出 8–15 个领域词，逐个在代码里找它唯一的落点；找不到落点或有多个落点的就是候选。

**脚本为什么看不到**：R6 只看目录名命中通用技术词、跨上下文关键词泄漏，报不出"一个词指两个概念"或"一个概念四个词"——它没有词表可比。

### 7. 一致性与单一事实源

**它在问**：这个值、这条规则、这份契约，改的时候需要记得改几个地方？

**真实长什么样**：
- 错误码在 enum、前端常量表、文档各写一遍。
- 超时 30s 在网关配置和客户端默认值各写一遍，已经不同步。
- 校验正则复制了三份，每份修过不同的分支。

**取证**：挑 3 个"外部会变的东西"（限额、费率、枚举、路径），grep 它们出现的所有位置。

**脚本为什么看不到**：R3 的字面量档只抓**数字**，且每个不同的字面量各出一条 Critical——真正需要人判的"两处表达同一决策"会被这些刷屏条目淹掉。

## 二、设计发现的输出契约（五段式，缺一项不算发现）

1. **决策是什么**：一句话，指到具体文件/符号。不许写"模块耦合过高"这类无主语句子。
2. **代价与收益**：各一条。写不出收益，说明你看到的是审美问题不是设计问题。
3. **我赌它错的依据**：可核查的观测（共变次数、grep 出的 N 处落点、第 4 条里那个具体变更），不是"通常认为"。
4. **若 X 变更发生会怎样**：X 必须是**有名字的真实变更**（下个季度的需求、准备接的第二家供应商、已在讨论的新字段），并说清要动几处、谁会先发现。
5. **为什么脚本看不到它**：回到 §一 对应类的机械化限制，指明是"没有实现"还是"实现了但口径不是这个"。

严重度**不由脚本给**，由第 4 条的到达时间定：本季度内发生 = High；已有讨论 = Medium；纯假设 = Low 或不提。

禁止的写法：「发现 N 个违规」「存在循环依赖风险」「建议重构」。这三类句子都没有决策、代价和条件。

## 三、什么时候不该报设计问题

先算收益再报，不是每条问题都值得占版面：

- 明确三年不扩张的小单体：§1 的边界问题不报，只报 §4（不变量归属）——它出错会直接产出错误结果。
- 一次性脚本、迁移工具、原型：§3、§5 不报。演化成本对不存在第二次的东西没有意义。
- 说不出第 4 条里那个具体变更：记成"观察"而不是"发现"，不占编号、不进门禁。

## 四、常被误当设计问题的（反向清单）

- **文件长 / MI 低**：长度问题。已实测：同一风格代码 332 行的文件可以低于 MI 15 的门、12 行的轻松过线。先拆文件再谈设计。
- **CC 高**：可能只是一个分支密集但边界正确的规则表达。高 CC 是"去读这个函数"的理由，不是结论。
- **循环依赖**：先判是不是组合根的装配环（假阳性防护见 `architecture-principles.md` §五），再谈依赖方向错。
- **测试数缩减、健康分下降**：这些是回归与阈值信号，属阶段三/五的账，不是设计发现。

## 五、怎么把它接进五阶段

顺序不能反：

1. **阶段零（先）**：读目录树、README/入口点、最近 20 次提交，把 §一 七类各问一遍，写出「待验证的设计问题清单」——可以为空，但空要说明每类各自看过什么证据。
2. 阶段一/二/三：跑脚本，用数据**缩窄或坐实**清单。脚本新报出来的东西可以进清单，但要重写成 §二 的五段式。
3. 阶段四/五：优化与回归防护只处理已定性为设计发现的条目。

反模式（要主动避免）：**先跑脚本、再按脚本的编号组织结论**。那样清单的来源就是阈值表，七类提问永远不会发生，产出与"读一眼报告"同构。
