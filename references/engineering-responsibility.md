# 工程责任参考文档

## 一、对工程负责（核心理念）

这是所有 skill 的根哲学。不管什么项目类型（软件、游戏、舆论分析、漏洞挖掘），第一原则是对工程负责。

### 1.1 定义
"对工程负责"意味着：交付的每一行代码、每一份文档、每一个决策，都必须经得起工程检验。不糊弄、不占位、不假实现、不推卸责任。

### 1.2 铁律
- 代码能跑还不够，必须能维护
- 功能实现还不够，必须理解为什么
- 短期交付还不够，必须考虑长期成本
- 对自己负责还不够，必须对团队和用户负责

### 1.3 工程>项目>其他（层级原则）
**工程决定项目，项目决定其他。** 这是所有工作的根本层级：

```
层级一：工程（Engineering）
  - 项目结构、目录约定、构建系统、CI/CD、依赖管理
  - 这是地基，必须最先搭好，永远不能跳过

层级二：项目（Project）
  - 业务逻辑、功能特性、具体实现
  - 在工程地基上建造，但不能破坏地基

层级三：其他（Other）
  - 优化、扩展、插件、额外功能
  - 只在项目跑通后考虑，不能干扰项目和工程
```

**实践规则**：
1. 新项目启动时，先花时间搭好工程结构（src/ + bin/ + docs/ + tests/ + 构建脚本）
2. 在工程结构到位之前，不写任何业务代码
3. 插件/扩展功能默认合并到根项目，不单独成项目
4. 任何破坏工程结构的行为（如乱放文件、跳过构建脚本）= Critical 违规

## 二、项目结构约定

### 2.1 统一目录原则
所有软件/游戏项目，必须在同一个项目文件夹内，分为：
```
<project-root>/
├── src/          # 源代码
├── bin/          # 编译后的二进制包/可执行文件
├── docs/         # 文档
├── tests/        # 测试
├── assets/       # 资源文件（游戏用）
└── tools/        # 工具脚本
```

### 2.2 源代码与二进制分离
- `src/` 只放源代码，不放编译产物
- `bin/` 放编译后的可执行文件、DLL、包
- `bin/` 下的内容可被 `.gitignore` 排除，但项目根目录必须保留 `bin/` 占位
- 游戏项目在 `bin/` 下区分 `bin/debug/` 和 `bin/release/`

### 2.3 工程之上才是其他
任何项目，先搭好工程结构，再谈业务逻辑。工程结构是地基，地基不稳，上层建筑毫无意义。

## 三、游戏开发约定

### 3.1 游戏项目结构
```
<game-project>/
├── src/              # 源代码（引擎代码、游戏逻辑）
│   ├── engine/       # 引擎核心
│   ├── game/         # 游戏逻辑
│   └── tools/        # 编辑器工具
├── bin/              # 编译产物
│   ├── debug/
│   └── release/
├── assets/           # 资源文件（纹理、模型、音频）
│   ├── raw/          # 原始资源（PSD、FBX、WAV）
│   └── processed/    # 处理后资源（PNG、GLTF、OGG）
├── docs/             # 游戏设计文档
└── tests/            # 测试
```

### 3.2 游戏开发原则
- 引擎与游戏逻辑分离：引擎可复用，游戏逻辑可热更新
- 资源管线自动化：raw → processed 必须有构建脚本
- 性能预算先行：每帧时间预算、内存预算、绘制调用预算
- 数据驱动：游戏参数以配置文件驱动，不硬编码

### 3.3 与 arch-optimize 的协同
- 游戏项目同样适用六大衰退风险扫描
- 游戏资源目录结构需纳入架构感知（阶段一）
- 游戏性能瓶颈需纳入质量度量（阶段三）

## 四、与其他 skill 的协同

### 4.1 与 ponytail 的协同
ponytail（懒散资深开发者模式）是"对工程负责"在编码层面的具体实践：
- 先问"这东西需要存在吗？" → 对工程负责的第一问
- 复用优先于重写 → 对现有代码负责
- 最小实现 → 对维护成本负责

### 4.2 与 MCP 的协同
- codebase-memory-mcp：代码知识图谱，加速对工程的理解
- srclight：本地代码语义搜索 + 调用图 + git 热点（完全本地零云依赖），提高工程质量

### 4.3 与 anti-ai-flavor 的协同
- 反 AI 味是"对工程负责"在内容真实性上的体现
- 假实现 = 对工程不负责，Blocker 禁止交付

### 4.4 与 opinion-system 的协同
- 舆论论证同样需要工程化的论证体系
- 知识库结构参照项目结构约定
- 多重后手机制 = 工程上的容错设计

### 4.5 与 vuln-hunting 的协同
- 漏洞挖掘是对工程安全的负责
- 发现漏洞后必须修复，不能只报告不修复
- 挖漏洞过程本身需要工程化（工具链、报告模板、复现步骤）

## 五、工程责任检查清单

### 5.1 交付前自查
- [ ] 项目结构是否遵循 src/ + bin/ 分离？
- [ ] 是否所有代码都有明确的 owner？
- [ ] 是否有回归测试覆盖关键路径？
- [ ] 是否有技术债务记录？
- [ ] 是否有已知漏洞未修复？
- [ ] 依赖是否最小化？
- [ ] 文档是否与实际代码一致？
- [ ] 是否通过了 AI 味检测？

### 5.2 长期维护承诺
- 技术债定期评估（每季度至少一次）
- 依赖版本定期更新（安全漏洞修复优先）
- 架构决策记录（ADR）持续维护
- 知识库持续更新
