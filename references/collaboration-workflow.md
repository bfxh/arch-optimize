## 一、设计理念

### 1.1 为什么需要双智能体


### 1.2 核心原则

- **战略与执行分离**：架构师管"做什么"，程序员管"怎么做"
- **信息隔离**：双方各自只能看到自己需要的信息
- **相互依赖**：架构师的需求质量影响程序员实现效果；程序员的实现质量影响下一轮分析
- **增量推进**：每次迭代最多5个需求，小步快跑

## 二、架构师角色 (Architect)

### 2.1 职责

1. **诊断分析**：研究所有失败的测试用例，找出共同模式和根本原因
2. **缺陷关联**：深入检查相关源代码，将抽象测试失败与具体代码缺陷关联
3. **方案设计**：设计增量式改进方案，每次最多提出5个最紧迫的改进需求

### 2.2 架构师工作流

```
Phase 1: 诊断 (Diagnose)
  输入: 测试结果 + 代码库
  动作:
    - 分析失败测试的共同模式
    - 定位相关源代码区域
    - 评估六大衰退风险 (R1-R6)
    - 计算 Pain × Spread 优先级
  输出: 诊断报告（含热点区域和风险评级）

Phase 2: 设计 (Design)
  输入: 诊断报告
  动作:
    - 针对每个热点设计改进方向
    - 按优先级排序（最多5个）
    - 编写高层次自然语言需求
    - 评估预期效果和风险
  输出: 改进需求列表（≤5项）
```

### 2.3 需求文档规范

架构师产出的需求文档必须遵循以下原则：

**增量性**：专注当前最迫切需求，避免过度设计

**高层次性**：用自然语言描述期望行为，不给出具体实现细节

**格式**：
```markdown
### 需求 #1: [简短标题]
- **优先级**: Pain×Spread = 9 (Critical)
- **关联风险**: R5 依赖失序
- **当前状态**: [描述问题和症状]
- **期望状态**: [描述期望的行为，不含实现细节]
- **影响范围**: [受影响的模块/功能]
- **风险评估**: [可能的副作用]
- **验证方式**: [如何验证改进是否成功]
```

**示例**：
```markdown
### 需求 #1: 消除 Agent 包与 Tool 包的循环依赖
- **优先级**: Pain×Spread = 9 (Critical)
- **关联风险**: R5 依赖失序
- **当前状态**: internal/agent 直接导入 internal/tool/builtin，
  而 internal/tool/builtin 通过 init() 注册时反向引用 agent.Session
- **期望状态**: Agent 依赖 Tool 接口（定义在 tool 包），
  内置工具通过注册表解耦，不反向引用 Agent
- **影响范围**: internal/agent/, internal/tool/, internal/tool/builtin/
- **风险评估**: 需修改工具注册机制，可能影响插件加载顺序
- **验证方式**: go vet ./... 无循环依赖警告；所有现有测试通过
```

### 2.4 架构师不做的事

- ❌ 不写具体代码实现
- ❌ 不指定使用哪个设计模式
- ❌ 不干预程序员的实现选择
- ❌ 不一次性提出超过5个需求
- ❌ 不跳过诊断直接给方案

## 三、程序员角色 (Programmer)

### 3.1 职责

1. **理解需求**：将自然语言描述的期望转化为明确的技术规格
2. **制定计划**：考虑如何在现有代码基础上进行修改
3. **代码编写**：具体的代码修改和实现
4. **测试验证**：运行测试套件确保变更正确

### 3.2 程序员工作流

```
Phase 1: 理解 (Understand)
  输入: 架构师需求文档 + 代码库
  动作:
    - 阅读需求，确认理解
    - 研究相关代码区域
    - 确认技术约束（语言、框架、依赖）
  输出: 技术规格草案

Phase 2: 规划 (Plan)
  输入: 技术规格草案
  动作:
    - 设计实现方案
    - 识别变更范围（文件列表）
    - 评估对现有功能的影响
    - 制定测试策略
  输出: 实现计划（含文件变更列表和测试计划）

Phase 3: 实现 (Implement)
  输入: 实现计划
  动作:
    - 执行代码修改
    - 遵循编码规范（见 coding-conventions.md）
    - 增量提交，每步可验证
  输出: 代码变更

Phase 4: 验证 (Verify)
  输入: 代码变更
  动作:
    - 运行完整测试套件
    - 检查回归（见 regression-guard.md）
    - 计算 MI 和健康分
    - 确认零退化率 = 100%
  输出: 验证报告
```

### 3.3 程序员的编码规范约束

程序员在实现时必须遵循 `coding-conventions.md` 中的规范：
- 函数 ≤50 行
- 嵌套 ≤3 层
- 参数 ≤4 个
- 错误必须处理或传播
- 无循环依赖
- 依赖方向正确

### 3.4 程序员不做的事

- ❌ 不修改需求范围（如需修改，反馈给架构师）
- ❌ 不跳过测试验证
- ❌ 不在未通过回归检查时声称完成
- ❌ 不引入未评估的新依赖

## 四、信息隔离规则

### 4.1 架构师可见信息

| 信息 | 可见 | 不可见 |
|------|------|--------|
| 测试结果 | ✅ | - |
| 代码库结构 | ✅ | - |
| 架构文档 | ✅ | - |
| 具体实现代码 | ✅（诊断时） | - |
| 目标解决方案 | - | ❌（不提供） |
| 程序员的实现计划 | - | ❌（不干预） |

### 4.2 程序员可见信息

| 信息 | 可见 | 不可见 |
|------|------|--------|
| 架构师需求文档 | ✅ | - |
| 相关源代码 | ✅ | - |
| 编码规范 | ✅ | - |
| 完整诊断报告 | - | ❌（只看需求） |
| 其他需求 | - | ❌（只看分配给自己的） |
| 目标解决方案 | - | ❌（不提供） |

## 五、反馈循环

### 5.1 单次迭代流程

```
    ┌──────────────────────────────────────────┐
    │              迭代开始                      │
    └──────────────┬───────────────────────────┘
                   │
                   ▼
    ┌──────────────────────────┐
    │   架构师: 诊断             │
    │   - 分析测试结果           │
    │   - 扫描六大风险           │
    │   - 定位热点区域           │
    └──────────────┬───────────┘
                   │
                   ▼
    ┌──────────────────────────┐
    │   架构师: 设计需求         │
    │   - 按优先级排序           │
    │   - 最多5个需求            │
    │   - 高层次自然语言         │
    └──────────────┬───────────┘
                   │
                   ▼
    ┌──────────────────────────┐
    │   程序员: 理解+规划        │
    │   - 转化为技术规格         │
    │   - 制定实现计划           │
    └──────────────┬───────────┘
                   │
                   ▼
    ┌──────────────────────────┐
    │   程序员: 实现             │
    │   - 遵循编码规范           │
    │   - 增量修改               │
    └──────────────┬───────────┘
                   │
                   ▼
    ┌──────────────────────────┐
    │   程序员: 验证             │
    │   - 运行测试套件           │
    │   - 检查回归               │
    │   - 计算 MI 和健康分       │
    └──────────────┬───────────┘
                   │
                   ▼
    ┌──────────────────────────┐
    │   反馈给架构师             │
    │   - 测试结果变化           │
    │   - 新的风险区域           │
    │   - 下轮迭代输入           │
    └──────────────────────────┘
```

### 5.2 多轮迭代演进

```
迭代 1: 架构师诊断 → 5个需求 → 程序员实现 → 验证 → 反馈
迭代 2: 架构师基于反馈重新诊断 → 5个新需求 → ...
迭代 3: ...
```


### 5.3 异常处理

| 异常情况 | 处理方式 |
|---------|---------|
| 程序员发现需求不可行 | 反馈架构师，重新设计需求 |
| 回归检测发现退步 | 程序员修复或回滚，架构师重新评估 |
| 需求超出单次迭代范围 | 架构师拆分为多个迭代 |
| 健康分下降 | 暂停迭代，进行根因分析 |

## 六、团队拓扑映射

来源：Team Topologies (Skelton & Pais)

### 6.1 架构师对应角色

架构师角色可映射为：
- **赋能团队 (Enabling)**：临时性，帮助流对齐团队掌握新技能/技术
- **复杂子系统团队 (Complicated-subsystem)**：处理需要 specialist 知识的复杂领域

### 6.2 程序员对应角色

程序员角色对应：
- **流对齐团队 (Stream-aligned)**：以业务能力为中心，长期运行，价值流最大化

### 6.3 交互模式

| 交互 | 模式 | 说明 |
|------|------|------|
| 架构师 → 程序员 | 促成 (Facilitating) | 赋能团队帮助流对齐团队 |
| 程序员 → 架构师 | 反馈 (Feedback) | 实现结果反馈影响后续设计 |
| 平台团队 → 程序员 | X-as-a-Service | 提供自服务平台降低认知负荷 |

## 七、与 Reasonix 架构的映射

Reasonix 项目的 `control.Controller` 设计天然适合双智能体协作：

```
架构师 Agent                    程序员 Agent
    │                               │
    │  高层次需求                    │  实现计划
    │──────────────────────────────→│
    │                               │
    │                    ┌──────────┤
    │                    │ control  │  统一控制器
    │                    │Controller│  (传输无关)
    │                    └──────────┤
    │                               │
    │  测试结果反馈                  │  代码变更
    │←──────────────────────────────│
    │                               │
```

Reasonix 的 `Coordinator`（双模型协作：planner + executor）已经实现了类似的分离：
- **planner_model** → 对应架构师（战略层）
- **executor** → 对应程序员（执行层）
- 会话分离保持缓存前缀稳定

本技能可进一步规范化这一协作模式，将其应用于架构优化场景。

## 八、子代理分发与批评家迭代 (Sub-Agent Dispatch & Critic Iteration)

在双智能体协作基础上，引入子代理分发机制与严格批评家迭代循环，进一步提升产出质量。批评家以 AAA 级为标准，对子代理产出进行多轮审查，直至质量达到"惊叹"水平。

### 8.1 分发策略

将架构优化任务分解为独立子任务，每个子代理负责一个方面：

- **任务分解**：将整体任务拆分为可独立执行的子任务，降低单个代理的认知负荷
- **接口协作**：子代理之间通过明确的输入/输出接口协作，避免隐式依赖
- **串行阶段**：架构师子代理和程序员子代理串行执行——架构师先出方案，程序员后实现
- **并行阶段**：视觉批评家子代理和回归守卫子代理可以并行执行，互不阻塞

### 8.2 批评家迭代循环

各子代理完成各自工作后，进入批评家主导的迭代循环：

1. 各子代理完成各自工作后，汇总产出
2. 视觉批评家子代理对所有产出进行 AAA 级审查
3. 如果不达 AAA 级，批评家输出具体改进建议
4. 相关子代理根据建议修改
5. 重新提交审查
6. 循环直到批评家对质量感到惊叹

迭代循环示意如下：

```
    ┌──────────────────────────────────────────┐
    │              迭代开始                      │
    └──────────────┬───────────────────────────┘
                   │
                   ▼
    ┌──────────────────────────┐
    │   子代理汇总产出          │
    │   - 架构师方案            │
    │   - 程序员实现            │
    │   - 回归守卫报告          │
    └──────────────┬───────────┘
                   │
                   ▼
    ┌──────────────────────────┐
    │   视觉批评家审查          │
    │   - AAA 级标准            │
    │   - 全维度评分            │
    └──────────────┬───────────┘
                   │
            ┌──────┴──────┐
            ▼             ▼
       达到 AAA 级      未达标
            │             │
            ▼             ▼
    ┌──────────────┐  ┌──────────────────────┐
    │   终止迭代    │  │  输出改进建议         │
    │   交付产出    │  │  - 问题位置           │
    └──────────────┘  │  - 改进建议           │
                      │  - 预期效果           │
                      └──────────┬───────────┘
                                 │
                                 ▼
                      ┌──────────────────────┐
                      │  相关子代理修改       │
                      └──────────┬───────────┘
                                 │
                                 └───→ 重新汇总产出（回到顶部）
```

### 8.3 批评家权限

- **全局否决权**：可以否决任何子代理的产出
- **否决必须附带**：问题位置、改进建议、预期效果
- **连续3次否决同一问题**：升级为人工审查
- **批评家标准**：看起来不像 AAA 级就否决，不接受"差不多"

### 8.4 迭代终止条件

三项条件同时满足才可终止迭代：

- 所有维度评分 ≥ 90分（AAA级）
- 无 Blocker 级问题
- 批评家主观评价为"惊叹"

### 8.5 与五阶段的集成

| 阶段             | 子代理   | 批评家审查点               |
|------------------|----------|----------------------------|
| 阶段一 架构感知  | 架构师   | 目录树和依赖图的可读性     |
| 阶段二 风险诊断  | 架构师   | 诊断报告的四段式完整性     |
| 阶段三 质量度量  | 架构师   | 度量数据的可视化呈现       |
| 阶段四 增量优化  | 程序员   | 代码的逐行可审视性         |
| 阶段五 回归防护  | 回归守卫 | 回归报告的清晰度           |
